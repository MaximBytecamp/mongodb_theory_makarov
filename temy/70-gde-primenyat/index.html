§1Одна карточка в двух моделях

В регистратуре поликлиники карточка пациента — одна папка. В ней лежат титульный лист, записи приёмов, бланки анализов. Врач берёт папку и читает всё сразу. Другой способ хранения — картотека из нескольких шкафов. В одном шкафу титульные листы, в другом записи приёмов, в третьем анализы. На каждом бланке стоит номер карточки, и по нему бланки сводят вместе.

Реляционная база устроена как картотека из шкафов. Каждый вид сведений хранится в своей таблице с постоянным набором столбцов. Записи разных таблиц связаны ключами, а при чтении их сводит соединение — операция JOIN. Документная база устроена как папка. Всё, что относится к одной сущности и читается вместе, лежит в одном документе. Внутри документа бывают вложенные документы и списки.

На схеме — карточка кошки в двух моделях: слева четыре таблицы, справа один документ.

Карточка животного: таблицы и документ

patients
id | name | species | breed | born
allergies
patient_id | substance

patient_id | vaccine | date | next
cat_details

Документная модель: 1 документ
{
_id, name, species, breed, born, allergies: [ "пенициллин" ], vaccinations: [ {vaccine, date, next}, … ], cat: { fiv, felv, indoor } }

Цвет показывает, какая таблица стала какой частью документа. Чтобы открыть карточку, реляционная база соединяет четыре таблицы; MongoDB читает один документ.

Обе модели хранят одни и те же сведения. Различается цена операций. Соединение таблиц занимает время при каждом чтении. Взамен каждый факт записан один раз, и связи проверяет сама база. Документ читается за одно обращение. Взамен часть правил о форме данных и о связях переходит к программе.

Поэтому выбор базы зависит от того, какие операции в задаче частые и какие ошибки в ней недопустимы. Остаётся понять, в каких задачах документ экономит больше работы, чем стоит.

§2Признаки данных, которым подходит документ

В таблице шесть признаков. Чем больше их совпадает с задачей, тем больше работы экономит документная модель. К каждому признаку дан пример из бизнеса.

ПризнакКак выглядит в бизнесеЧто даёт документ

Первый признак встречается чаще остальных. В реляционной базе разнородные записи хранят тремя способами, и у каждого есть недостаток.

  • Общая таблица со всеми возможными столбцами. У кошки остаются пустыми столбцы черепахи.
  • Отдельная таблица на каждый вид. Новый вид требует новой таблицы и правки программы.
  • Характеристики строками «запись — имя — значение». Такой способ называют EAV (entity–attribute–value). Значения разных типов лежат в одном текстовом столбце, а одна карточка собирается из многих строк.

В MongoDB у каждого документа свой набор полей, и выбирать между этими способами не нужно. У тех же свойств документа есть обратная сторона, и для части задач она перевешивает.

§3Признаки, при которых удобнее реляционная база

Документ удобен, пока данные читают так, как их сложили. Когда одни и те же сведения нужны в разных сочетаниях, а ошибка в них стоит денег, реляционная база выполняет больше проверок сама.

Деньги и остатки

Перевод между счетами, списание со склада по нескольким позициям, начисление зарплаты. Ошибка в одной записи из пары даёт расхождение в деньгах.

MongoDB поддерживает транзакции по нескольким документам с версии 4.0. Реляционные базы строились вокруг транзакций с самого начала, и бухгалтерские программы работают с SQL.

Много связей многие-ко-многим

Студенты, группы, преподаватели, аудитории, расписание. Каждая сущность связана с несколькими другими.

При вложении сведения повторяются в нескольких документах. При ссылках почти каждый запрос становится соединением через $lookup.

Произвольные отчёты

Аналитики каждый день задают новые вопросы и сводят данные по любым полям.

Документы проектируют под заранее известные запросы. Для свободной аналитики данные обычно выгружают в хранилище с SQL.

Строгая проверка ссылок

Справочники, где ссылка обязана вести на существующую запись, а запись, на которую ссылаются, удалять нельзя.

Внешних ключей в MongoDB нет. Ссылки проверяет программа.

Второй признак виден на расписании колледжа. Преподаватель Орлова ведёт пары у двух групп. Если собрать документ вокруг группы, сведения о преподавателе повторятся в документе каждой группы. В реляционной базе преподаватель записан один раз, а пары ссылаются на него.

Оранжевым выделены сведения об одном преподавателе. Слева они записаны дважды, справа — один раз. Расписание преподавателя слева собирается из всех документов групп, справа — отбором строк одной таблицы.

Такие признаки редко относятся ко всей системе. Часть данных подходит документу, часть — таблицам, и в одной системе работают обе базы. Чтобы разделить данные, нужен список типов данных, которые встречаются в задачах бизнеса.

§4Типы данных и приёмы для них

Строки таблицы не привязаны к отрасли. Ветеринарная карточка, страховой полис и объявление о квартире относятся к одному типу: общие поля и особые поля по типу объекта. Поэтому один приём хранения подходит всем трём. У каждого приёма есть выигрыш для бизнеса и своя цена.

§5Что получает бизнес и чем за это платит

Выигрыш от документной модели виден в трёх местах.

  • Время разработки. Новое поле или новый вид записи не требует перестройки таблиц. Изменения в работе компании быстрее попадают в программу.
  • Скорость частых экранов. Карточка, заказ, профиль читаются одним обращением к базе.
  • Объём. Коллекцию можно распределить по нескольким серверам, когда данные перестают помещаться на одном. Такое распределение называют шардированием.

У каждого выигрыша есть цена. Сведения, вложенные в несколько документов, обновляют в каждом из них. Правила формы данных в таблице задаёт схема, а в MongoDB — валидатор $jsonSchema (глава 3.1) или программа. Без них в коллекции накапливаются документы разной формы. Документ ограничен 16 МБ, и растущий без предела список однажды в него не поместится. Этот случай разобран в разделе Кейсы.

ВыигрышЦенаКак снижают цену

Выигрыши и цены зависят от задачи. Поэтому решение принимают по шагам, начиная с экранов и операций системы.

§6Порядок принятия решения

Порядок подходит для любой предметной области. Решение принимается по задачам системы. Название технологии и привычки команды в нём не участвуют.

  1. Перечислить экраны и отчёты. Что открывает каждый сотрудник и клиент, какие отчёты нужны руководителю. Для клиники: экран врача, расписание, напоминания, сводка для закупки.
  2. Для каждого экрана — какие сведения читаются вместе. Если почти все экраны строятся вокруг одной сущности (животное, заказ, заявка), это признак документа.
  3. Найти операции, которые должны пройти целиком по нескольким записям. Оплата, списание остатков, перевод денег. Чем их больше и чем дороже ошибка, тем больше доводов за реляционную базу.
  4. Оценить, как часто меняется структура. Новые виды товаров, анализы, вопросы анкет — признак документа.
  5. Оценить объём и скорость роста. Тысячи записей в день или тысячи в секунду. Растут ли списки внутри сущности без предела.
  6. Разделить данные по базам, если признаки расходятся. Карточки и события — в MongoDB, деньги — в реляционную базу.

Ошибки при выборе базы повторяются из проекта в проект. Они собраны в следующей таблице.

§8Проверьте себя

У страховой компании полисы ОСАГО, ипотечного страхования и страхования путешественников. Какой признак документа здесь есть?

Набор полей зависит от типа записи. У ОСАГО — автомобиль и водители, у ипотеки — объект недвижимости и банк, у путешествия — страны и даты. Общие поля (номер, страхователь, срок, премия) лежат на верхнем уровне, особые — во вложенном документе по типу полиса.

Почему расписание колледжа удобнее хранить в реляционной базе?

Группы, преподаватели и аудитории связаны многие-ко-многим. Запросы нужны во всех сочетаниях: расписание группы, преподавателя, аудитории. Документ вокруг группы повторяет сведения о преподавателе и подходит только для расписания группы.

Что такое EAV и чем он хуже документа для карточек с разными полями?

EAV — хранение характеристик строками «запись — имя — значение» в реляционной таблице. Значения разных типов попадают в один текстовый столбец, а карточка собирается из многих строк. В документе поле хранит значение своего типа, и карточка читается целиком.

Какие два вопроса о списке внутри документа задают до проектирования?

Ограничен ли список по размеру и читается ли он вместе с документом. Прививки животного ограничены и нужны на экране врача — их вкладывают. Приёмы за всю жизнь животного растут без предела — их выносят в отдельную коллекцию.

Какой шаг порядка принятия решения выявляет операции, требующие транзакций?

Третий: поиск операций, которые должны пройти целиком по нескольким записям, — оплаты, списания остатков, переводов денег.

§9Шпаргалка

За таблицыденьги и остатки многие-ко-многим произвольные отчёты проверка ссылок базой

Порядок решенияэкраны → что читается вместе → атомарные операции → изменчивость → объём → разделить по базам

Итог главы

Реляционная база хранит сведения в таблицах с постоянными столбцами и сводит их соединениями. Документная база хранит вместе то, что читается вместе. MongoDB экономит работу в шести случаях: набор полей зависит от типа записи, сущность читается целиком, списки внутри неё ограничены, структура часто меняется, записи идут потоком или описывают состояние процесса.

Реляционная база удобнее для денег и остатков, связей многие-ко-многим, произвольной аналитики и проверки ссылок. Решение принимают по экранам и операциям системы, и нередко данные делят между двумя базами.
