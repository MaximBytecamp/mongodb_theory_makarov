Индексы: одиночные,
составные, уникальные

В этой главе разобрано, что такое индекс и как он меняет способ, которым сервер ищет документы. На копии журнала событий строятся индекс по одному полю и составной индекс по двум полям; по стадиям плана видно, когда сервер читает индекс, а когда — всю коллекцию. Отдельно разобраны уникальный индекс, который не пускает в коллекцию повторы, и частичный индекс для документов, в которых нужного поля нет.

§1Как сервер ищет без индекса

Запрос {"service": "payments"} к журналу событий находит 232 документа из 1200. Сервер заранее не знает, в каких документах записан сервис payments. Он читает все 1200 документов по порядку и у каждого проверяет поле service: 232 документа подходят, 968 прочитаны и отброшены. Такой способ называется просмотром коллекции (collection scan, в плане запроса — стадия COLLSCAN).

Так ищут слово в книге, у которой нет предметного указателя. Чтобы найти все страницы со словом «платёж», книгу листают от первой страницы до последней. В книге на 1200 страниц просматриваются все 1200, даже если слово встречается на 232. На 1200 документах просмотр занимает доли миллисекунды, на десяти миллионах — секунды. Чем больше коллекция, тем дольше выполняется каждый такой запрос.

На схеме — первые 40 событий журнала и два способа найти среди них события payments.

С индексом по service: IXSCAN и FETCH

Квадрат — один документ, число — конец его _id: 18 означает e-00018. Зелёные квадраты — события payments. Сплошная рамка — документ, который сервер прочитал; пунктирная — документ, который не читался.

В книге эту работу сокращает предметный указатель в конце: слова стоят в нём по алфавиту, при каждом слове записаны номера страниц. Читатель находит слово и открывает только названные страницы. В MongoDB ту же роль выполняет индекс. Индекс — отдельная структура рядом с коллекцией, в которой значения выбранного поля хранятся по порядку, и при каждом значении записаны ссылки на документы с этим значением. Ссылка — запись о том, где документ лежит на диске; по ней сервер читает документ сразу, без поиска.

В индексе 1200 записей, по одной на каждый документ, и они сгруппированы по пяти значениям поля. Значения стоят по алфавиту, поэтому сервер не читает индекс с начала: он сразу переходит к payments, как читатель открывает указатель на нужной букве. При этом значении записаны 232 ссылки, и сервер читает только эти 232 документа. Остальные 968 не читаются.

Полоса — весь индекс слева направо, от первой записи до последней. Ширина участка соответствует числу записей. Участки идут по алфавиту значений: от api-gateway до search.

Документы при создании индекса не меняются и не переставляются. В книге с указателем страницы тоже остаются на своих местах, указатель печатается отдельно.

Один индекс у каждой коллекции есть всегда — по полю _id, его создаёт сервер вместе с коллекцией. Поэтому поиск по _id быстрый с самого начала. Поиск по остальным полям становится быстрым после того, как для них создан индекс.

Индексы этой главы строятся на копии журнала в песочнице. База logs остаётся без новых индексов, и примеры других глав работают с ней в исходном виде. Копия — коллекция sandbox.events; в заготовке главы она открыта в переменной journal. Пример выполняет три действия: удаляет коллекцию journal (вместе с коллекцией удаляются все её индексы), копирует в неё события из logs.events и выводит список индексов.

В копии 1200 событий и один индекс. У каждого индекса есть ключ и имя. Ключ индекса — запись о том, по какому полю и в каком порядке упорядочен индекс. Ключ {"_id": 1} читается «по полю _id, по возрастанию»: 1 — по возрастанию, -1 — по убыванию. Имя индекса сервер составляет из ключа: имя поля, подчёркивание, направление. Индекс с ключом {"service": 1} получит имя service_1. У индекса по _id имя особое — _id_.

Индексы коллекции показывает вкладка Indexes, её счётчик — 1. В таблице одна строка, _id_. Столбцы таблицы:

  • Name & Definition — имя индекса; стрелка слева раскрывает его ключ;
  • Type — вид индекса; REGULAR — обычный;
  • Size — сколько места индекс занимает на диске;
  • Usage — сколько раз индекс использовался в запросах с указанной даты;
  • Properties — свойства индекса; у _id_ свойство UNIQUE, потому что двух документов с одним _id быть не может;
  • Status — состояние; READY означает, что индекс построен.

§2Индекс по одному полю

По результату запроса нельзя узнать, каким способом сервер искал документы: с индексом и без него программа получает одни и те же 232 документа. Способ виден в плане запроса — описании шагов, которыми сервер выполняет запрос. Шаги плана называются стадиями. План возвращает метод explain; подробно он разобран в главе 3.3.

В этой главе из плана нужны только названия стадий. Их достаёт функция plan из заготовки главы. Она принимает коллекцию и фильтр и возвращает строку со стадиями, например FETCH → IXSCAN service_1.

В главе встречаются четыре стадии. В правом столбце — то же действие с книгой из §1.

СтадияЧто делает серверТо же действие с книгой
COLLSCANЧитает все документы коллекции и проверяет условие у каждогоЛистает книгу от первой страницы до последней
IXSCAN service_1Находит нужное значение в индексе service_1 и получает ссылки на документыНаходит слово в указателе и выписывает номера страниц
FETCHЧитает документы по ссылкам, которые получила стадия IXSCANОткрывает страницы по выписанным номерам
SORTСортирует прочитанные документы в памяти сервераРаскладывает найденные страницы в нужном порядке

Строка плана читается справа налево: правая стадия выполняется первой и передаёт результат стадии слева. Строка FETCH → IXSCAN service_1 означает, что сервер сначала нашёл ссылки в индексе service_1, затем прочитал по ним документы. Стадии IXSCAN и FETCH идут парой: в индексе лежат только значения поля и ссылки, а запрос возвращает документы целиком, и их нужно прочитать.

Порядок выполнения двух планов, слева направо. Числа — из вывода примера ниже.

COLLSCANчитает все 1200 документов, у каждого проверяет serviceбез индекса · 1 стадия
программаполучает 232 документарезультат
IXSCAN service_1находит payments в индексе и получает 232 ссылкис индексом · 1-я стадия
FETCHчитает 232 документа по ссылкамс индексом · 2-я стадия
программаполучает 232 документарезультат

В строке плана стадии записаны в обратном порядке: FETCH → IXSCAN service_1. Слева стоит стадия, которая выполняется последней и отдаёт документы программе.

Пример выводит план запроса {"service": "payments"}, создаёт индекс по полю service и выводит план того же запроса ещё раз.

Индекс создаёт метод коллекции create_index. Одно поле можно передать строкой, направление тогда — по возрастанию. Метод возвращает имя созданного индекса.

Индексами коллекции управляет объект indexes; метод create_one создаёт индекс по документу ключа { "service" => 1 }. Он возвращает ответ сервера; имя индекса берётся методом indexes.get по тому же ключу.

Индексами коллекции управляет Indexes(); метод CreateOne принимает mongo.IndexModel, где в поле Keys записан ключ индекса, и возвращает имя созданного индекса.

Метод коллекции create_index принимает документ ключа и возвращает документ ответа, в котором имя индекса лежит в поле name.

До создания индекса план — COLLSCAN: сервер прочитал все 1200 документов. Метод вернул имя нового индекса, service_1. После этого план того же запроса состоит из двух стадий: IXSCAN service_1 нашла в индексе значение payments и получила 232 ссылки, FETCH прочитала по ним 232 документа.

Запрос в программе остался прежним: в обоих вызовах функции plan один и тот же фильтр. Сервер сам проверяет, есть ли у коллекции подходящий индекс, и использует его. Событий payments найдено 232, как и без индекса: индекс меняет способ поиска, результат запроса остаётся прежним.

Счётчик вкладки — 2, вторая строка — service_1, тип REGULAR, свойств у него нет: индекс не уникальный и не составной.

§3Составной индекс и порядок полей

Дежурный ищет ошибки сервера в платёжном сервисе: {"service": "payments", "status": {"$gte": 500}}. В запросе два условия: сервис payments и статус от 500. Индекс service_1 помогает только с первым условием. Он отбирает 232 события payments, сервер читает все 232 документа и у каждого проверяет статус. Подходят 42 документа, остальные 190 прочитаны и отброшены.

Чтобы индекс помогал с обоими условиями, в него включают оба поля. Составной индекс — индекс по нескольким полям. Записи в нём упорядочены сначала по первому полю, а внутри одинаковых значений первого поля — по второму.

В первых двух столбцах нужные строки стоят подряд. Сервер находит первую из них и читает вниз, пока строки подходят. В третьем столбце строки со статусом 503 разделены чужими строками, и прочитать их одним участком нельзя.

Почему поиск только по status не работает

В упорядоченном списке сервер ищет так же, как читатель ищет слово в словаре: открывает список в середине, сравнивает запись с искомым значением и по результату идёт выше или ниже. Для условия service = "payments" сравнение даёт ответ: запись "orders", 503 стоит раньше, чем нужно, значит, все записи выше неё тоже не подходят, и искать нужно ниже.

Для условия status = 503 сравнение ответа не даёт. Запись "orders", 503 подходит, запись "payments", 200 сразу под ней не подходит, а ещё ниже есть подходящая "payments", 503. По одной записи нельзя определить, в какой стороне лежат остальные: статусы идут по возрастанию только внутри одного сервиса, а на границе сервисов счёт начинается заново с 200. Поэтому запрос только по status сервер выполняет просмотром коллекции.

Префикс индекса

Первое поле составного индекса или несколько его первых полей подряд называются префиксом. Сервер использует составной индекс, когда в условиях запроса есть его префикс. Для индекса по service и status:

  • запрос по service — индекс помогает: service — префикс, нужные записи стоят одним участком;
  • запрос по service и status — индекс помогает: в запросе есть оба поля, нужные записи стоят одним участком внутри сервиса;
  • запрос только по status — индекс не помогает: поля service в запросе нет, нужные записи стоят в пяти местах.

Порядок полей задаётся при создании индекса. Индекс по status и service состоит из тех же 1200 записей, но упорядочен сначала по статусу, а внутри статуса — по сервису. Его префикс — status.

Отсюда правило выбора порядка: первым в составном индексе ставят поле, условие на которое есть в каждом запросе. Дежурный всегда указывает сервис и не всегда указывает статус, поэтому в примере ниже индекс строится по service, затем по status.

Составной индекс задаётся списком пар «поле, направление». Порядок пар в списке и есть порядок полей в индексе.

Составной индекс задаётся хешем из нескольких полей. Хеш Ruby сохраняет порядок ключей, и порядок полей в нём — порядок полей в индексе.

Составной индекс задаётся в Keys документом bson.D из нескольких полей. bson.D сохраняет порядок, и он становится порядком полей в индексе.

Составной индекс задаётся документом из нескольких полей; порядок полей в документе — порядок полей в индексе.

Пример создаёт индекс по service и status и выводит планы трёх запросов: по обоим полям, только по status и по service с сортировкой по status.

  • по обоим полям — FETCH → IXSCAN service_1_status_1. Сервер выполнил запрос по новому индексу;
  • только по status — COLLSCAN. Поле status не входит в префикс, сервер читает всю коллекцию;

Внутри значения payments записи индекса уже упорядочены по статусу, и сервер отдаёт документы в порядке индекса. В списке колледжа студенты одной группы тоже уже стоят по фамилиям, отдельно сортировать их не нужно.

Для первого запроса подходили два индекса: service_1 и составной. Когда подходят несколько индексов, сервер пробует их на запросе и оставляет тот, по которому результат получается за меньшее число шагов. По составному индексу читаются 42 документа, по service_1 — 232, и сервер выбрал составной.

В дереве те же две стадии, что вывела функция plan: снизу IXSCAN по индексу service_1_status_1, над ней FETCH, обе вернули 42 документа. Справа сводка: прочитано 42 ключа индекса и 42 документа — столько же, сколько найдено. Остальные числа сводки разобраны в главе 3.3.

§4Удаление индекса

После создания составного индекса у коллекции два индекса, которые начинаются с поля service: service_1 и service_1_status_1. Запрос по одному service может выполнить любой из них, потому что service — префикс составного индекса. Список колледжа, упорядоченный по группе и фамилии, уже позволяет найти всех студентов группы; второй список, упорядоченный только по группе, ничего к нему не добавляет.

Индекс service_1 стал лишним. Он занимает место на диске, и при каждой записи в коллекцию сервер обновляет и его (§8). Лишний индекс удаляют. Индекс удаляется по имени.

Остались два индекса — _id_ и составной. Запрос по service выполнен по составному индексу: service — его префикс.

Во втором плане первой стоит стадия SORT. Индекс отдаёт события payments в порядке статусов, а запрос требует порядок по времени ts. В списке колледжа так выглядит запрос «студенты группы ИС-22 по дате рождения»: участок группы находится сразу, но внутри него фамилии стоят по алфавиту, и по дате рождения их раскладывают отдельно. §5Уникальный индекс

При регистрации на сайте форма отвечает «эта почта уже занята», если на такой адрес уже заведена учётная запись. В базе данных эту проверку выполняет уникальный индекс. Индекс с параметром unique — уникальный — не допускает в коллекции двух документов с одинаковым значением индексированного поля.

Сервер проверяет это при каждой вставке и каждом обновлении. Он ищет новое значение в индексе, и если оно там уже есть, отклоняет запись: документ не записывается, программа получает ошибку. Так же приходит отказ валидатора из главы 3.1. Значение в индексе находится быстро, поэтому для проверки сервер не читает коллекцию.

Порядок проверки для записи из примера ниже:

insert_oneновый покупатель Ольга Кравец, почта user01@example.com1 · запись
индекс email_1значение user01@example.com в индексе уже есть: это почта Анны Беловой2 · проверка
ответкод 11000, документ не записан3 · отказ

Уникальным индексом защищают значения, которые должны встречаться один раз: почту покупателя, номер заказа, артикул товара.

Пример копирует покупателей из shop.customers в clients (sandbox.customers), создаёт уникальный индекс по полю email и пробует записать нового покупателя с почтой, которая уже есть у Анны Беловой.

Параметр передаётся в create_index именованным аргументом unique=True. Отказ из-за повтора PyMongo выбрасывает исключением DuplicateKeyError; повторившееся значение лежит в e.details["keyValue"].

Параметр передаётся в create_one вторым аргументом unique: true. Отказ приходит исключением Mongo::Error::OperationFailure; повторившееся значение лежит в ответе сервера, e.document["writeErrors"][0]["keyValue"].

Параметры индекса собираются в options.Index(), уникальность задаёт SetUnique(true). Отказ приходит ошибкой mongo.WriteException; повторившееся значение достаёт Raw.Lookup("keyValue") из первой ошибки записи.

Параметры индекса — объект mongocxx::options::index, уникальность задаёт unique(true). Отказ приходит исключением mongocxx::operation_exception; повторившееся значение лежит в ответе сервера, в первом элементе writeErrors.

Индекс получил имя email_1. Вставка отклонена с кодом 11000. Название этой ошибки — DuplicateKey, «повтор ключа»; ключом здесь называется значение индексированного поля. Поле keyValue в ответе сервера называет значение, которое уже есть в индексе: почту user01@example.com. Покупателей по-прежнему 20: отклонённый документ не записан.

У индекса email_1 свойство UNIQUE, как у _id_: оба не допускают повторов. Документов на вкладке Documents — 20.

§6Уникальный индекс на данных с повторами

Уникальный индекс можно создать только на коллекции, где повторов уже нет. Создавая индекс, сервер проходит по всем документам и заносит в индекс значение из каждого. Если очередное значение в индекс уже занесено, требование «без повторов» нарушено самими данными, и сервер прекращает создание индекса.

Так же нельзя объявить номера зачётных книжек уникальными, пока в списке группы у двух студентов записан один номер. Сначала исправляют список, затем вводят правило.

Пример считает, сколько разных городов у покупателей, и пробует создать уникальный индекс по полю city.

Городов пять на 20 покупателей, значит, города повторяются. Индекс не создан, код ошибки тот же, что при вставке повтора, — 11000. В списке индексов коллекции его нет: там по-прежнему _id_ и email_1. Перед созданием уникального индекса на коллекции с данными повторы находят и устраняют.

В PyMongo отказ при постройке приходит тем же исключением DuplicateKeyError; пример ловит его через общий класс OperationFailure, от которого наследуются все ошибки сервера.

Отказ при постройке приходит ошибкой команды mongo.CommandError; код лежит в её поле Code.

§7Документ без поля и частичный индекс

В уникальный индекс заносятся все документы коллекции, в том числе те, в которых индексированного поля нет. Для такого документа в индекс записывается значение null — «значения нет».

Сравнение — картотека анкет, в которой у двух анкет не может совпадать графа «почта». Анкета с незаполненной графой тоже стоит в картотеке, и в этой графе у неё прочерк. Первый прочерк допустим. Второй прочерк совпадает с первым, и по правилу картотеки это повтор. С индексом так же: при уникальном индексе по email без почты может быть только один покупатель, второй даст повтор значения null. Пример добавляет двух покупателей без почты.

Если документы без поля допустимы, индекс делают частичным. Частичный индекс содержит не все документы коллекции: параметр partialFilterExpression задаёт условие, и в индекс попадают только документы, которые ему соответствуют. Условие {"email": {"$exists": true}} читается «поле email в документе есть». Документы без почты в такой индекс не заносятся, значений null в нём нет, и уникальность проверяется только среди документов с почтой.

Параметры существующего индекса изменить нельзя. Поэтому пример удаляет email_1 и создаёт индекс заново, уже с условием.

Параметр передаётся в create_index именованным аргументом partialFilterExpression, значение — документ условия.

Параметр передаётся в create_one как partial_filter_expression:, значение — документ условия.

Условие задаёт SetPartialFilterExpression в той же цепочке options.Index(), что и SetUnique.

Условие задаёт partial_filter_expression объекта параметров. Объект хранит ссылку на документ условия, поэтому документ лежит в отдельной переменной has_email и живёт до создания индекса.

Первый покупатель без почты записан, второй отклонён: в keyValue стоит почта со значением null (Python печатает его как None). После замены индекса частичным второй покупатель записан, покупателей без почты теперь двое. Повтор почты user01@example.com частичный индекс по-прежнему отклоняет.

У нового email_1 два свойства: UNIQUE и PARTIAL — «частичный». Значок i рядом со свойством показывает условие индекса. Документов 22: к двадцати покупателям добавились двое без почты.

§8Какие поля индексировать

Индекс ускоряет чтение и замедляет запись. В книгу с тремя указателями новая страница добавляется в четыре действия: сама страница и запись в каждом указателе. Сервер работает так же: при каждой вставке, обновлении и удалении он меняет документ и каждый индекс коллекции.

У копии журнала после §4 два индекса. Вставка одного события состоит из трёх действий:

insert_oneв журнал добавляется одно событиезапись
коллекциядокумент записандействие 1
индекс _id_добавлена запись с новым _idдействие 2
индекс service_1_status_1запись вставлена на своё место по сервису и статусудействие 3

Индекс занимает место на диске. На копии журнала из 1200 событий составной индекс занимает 24,6 kB (кадр в §4), и размер растёт вместе с коллекцией. У одной коллекции может быть не больше 64 индексов.

Поэтому индексы строят под запросы, которые выполняются часто: поиск дежурного по сервису и статусу, вход покупателя по почте. Поле, по которому почти не ищут, индексировать не нужно.

Польза от индекса зависит от того, сколько разных значений у поля. У поля level три значения на 1200 событий, и значение info стоит у 777 из них. По индексу сервер получит 777 ссылок и прочитает 777 документов — больше половины коллекции. Указатель, в котором при слове записано больше половины страниц книги, чтение почти не сокращает. У почты покупателя каждое значение встречается один раз, и по индексу читается один документ.

Индекс создают для поля:

  • по которому часто ищут или сортируют;
  • у которого много разных значений;
  • значения которого не должны повторяться, — тогда индекс уникальный.

Индексировать можно и вложенные поля, и поля массивов. Ключ записывается точечной нотацией, как в фильтре (глава 2.1): {"delivery.city": 1} — индекс по городу доставки заказа. Если поле — массив или лежит внутри массива, как items.sku, сервер заносит в индекс каждый элемент отдельно. Такой индекс называется многоключевым (multikey) и находит заказ по любому из его артикулов. В предметном указателе одна страница тоже записана при нескольких словах — при каждом, которое на ней встречается.

§9Индексы в Compass

Кадры в разделах выше сняты на тех же коллекциях, что и примеры. Индексы коллекции в Compass находятся на вкладке Indexes; таблица индексов разобрана в §1.

Кнопка Create Index открывает окно создания индекса.

В строке Index fields выбирается поле и тип: 1 или -1 — направление, как в коде. Кнопка + справа добавляет строку для следующего поля составного индекса. В разделе Options — параметры: Create unique index делает индекс уникальным, Index name задаёт своё имя вместо составленного сервером, Partial Filter Expression — условие частичного индекса. Остальные параметры окна в этой главе не используются. Кнопка Create Index внизу станет активной, когда выбрано хотя бы одно поле с типом.

Удаляется индекс из строки таблицы: при наведении курсора в конце строки появляются кнопки Hide Index (скрыть индекс от планировщика запросов, не удаляя) и Drop Index (удалить).

Использует ли запрос индекс, Compass показывает кнопкой Explain на вкладке Documents (кадр в §3): для запроса из поля фильтра строится тот же план, что возвращает метод explain, в виде дерева стадий.

§11Проверьте себя

Чем план COLLSCAN отличается от FETCH → IXSCAN?

При COLLSCAN сервер читает все документы коллекции и проверяет условие у каждого. При IXSCAN он находит нужные значения в упорядоченном индексе и получает ссылки на подходящие документы, а FETCH читает только их.

Есть индекс по service и status. Каким из запросов он поможет: по service, по status, по обоим полям?

Запросу по service и запросу по обоим полям. service — префикс индекса; записи с одним значением status разбросаны по разным сервисам, и запрос только по status выполняется просмотром коллекции.

Когда в плане появляется стадия SORT?

Когда порядок, заданный сортировкой, не совпадает с порядком записей в индексе, по которому выполнен запрос, — например, при сортировке по ts с индексом по service и status. Тогда сервер сортирует прочитанные документы в памяти.

Почему не создаётся уникальный индекс по city?

В коллекции уже есть покупатели с одинаковым городом. При постройке сервер проходит по всем документам и останавливается на первом повторе с ошибкой 11000.

Зачем уникальному индексу по email условие {"email": {"$exists": true}}?

Без условия документы без почты попадают в индекс со значением null, и второй такой документ даёт повтор. С условием они в индекс не попадают, и уникальность проверяется только среди документов с почтой.

Итог главы

Индекс хранит значения полей коллекции упорядоченно, со ссылками на документы, и позволяет серверу найти документы без просмотра всей коллекции: в плане запроса вместо COLLSCAN появляется IXSCAN с именем индекса и FETCH. Индекс по _id есть у каждой коллекции, остальные создаются явно и удаляются по имени. Составной индекс упорядочен по первому полю, затем по второму и помогает запросам, условия которых начинаются с его префикса; если сортировка совпадает с порядком индекса, стадии SORT в плане нет. Уникальный индекс отклоняет повтор значения с ошибкой 11000 и не создаётся на данных, где повторы уже есть; документ без поля попадает в индекс со значением null, и частичный индекс с условием partialFilterExpression исключает такие документы. Каждый индекс замедляет запись и занимает место, поэтому индексы строят под частые запросы.
