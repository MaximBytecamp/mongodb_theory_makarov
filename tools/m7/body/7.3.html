§1Каталог, где у каждого товара свои характеристики

На полке зоомагазина у каждого товара свой ценник. На корме написан вес упаковки, на переноске — размеры, на лампе — мощность. При клинике работает такой магазин, и его каталог хранится в базе. Покупатель выбирает товар через панель фильтров: отмечает «собака» и «от 10 кг» и получает список подходящих кормов. На схеме — характеристики пяти из шести категорий файла данных главы.

Характеристики по категориям каталога
КатегорияХарактеристики
кормвид, вес, возраст, вкус, лечебный, белок
переноскавид, длина, ширина, высота, нагрузка, вентиляция
освещениевид, мощность, UVB, срок замены
лекарствовид, рецептурный, объём, хранение
клеткавид, длина, ширина, высота, материал

Общая для всех категорий только характеристика «вид». Остальные встречаются в одной-двух категориях.

В большом интернет-магазине категорий тысячи, и у каждой свой список характеристик. Столбец под каждую характеристику сделает таблицу широкой и почти пустой. Отдельное поле документа под каждую характеристику тоже создаёт трудность. Быстро искать по полю можно только с индексом, а индексов на коллекцию не больше 64.

Загрузите файл данных главы. Он создаёт коллекции zoo_catalog (12 товаров) и zoo_forms (4 анкеты) и индекс по характеристикам. Характеристики в zoo_catalog хранятся так, чтобы один индекс служил всем.

§2Шаблон атрибутов

В товарной накладной характеристики записаны строками «наименование — значение — единица». Каталог хранит их так же. Общие для всех товаров поля — название, категория, цена — лежат на верхнем уровне документа. Характеристики собраны в массив attrs. Каждый элемент массива — пара:

  • k (key) — имя характеристики;
  • v (value) — значение;
  • u — единица измерения, если она нужна.

Такая раскладка называется шаблоном атрибутов. Так выглядят корм и террариум.

Общая у двух товаров только характеристика «вид», а форма документов одинакова: массив пар. Значения сохраняют свой тип. Вес 15 и объём 121 — числа, их сравнивают операторами $gte и $lt. Вкус и материал — строки. В EAV реляционной таблицы все значения лежали бы в одном текстовом столбце. На схеме — те же два товара с отдельным полем на каждую характеристику и в шаблоне атрибутов.

Отдельные поля и массив пар
Поле на каждую характеристику
{ weight_kg: 15, age: "взрослые", taste: "индейка" }
{ volume_l: 121, material: "стекло" }
индекс на weight_kg, индекс на volume_l, …
шаблон атрибутов
Массив пар
attrs: [ {k:"вес", v:15, u:"кг"}, {k:"вкус", v:"индейка"} ]
attrs: [ {k:"объём", v:121, u:"л"}, {k:"материал", v:"стекло"} ]
один индекс { "attrs.k": 1, "attrs.v": 1 }

Слева каждой новой характеристике нужен свой индекс. Справа новая характеристика — новая пара в массиве, индекс один на все.

По массиву пар нужно искать так, чтобы имя и значение относились к одной паре. Для этого служит отдельная запись условия.

§3Поиск по нескольким характеристикам

Продавец ищет на складе коробку, у которой на одной наклейке написано «корм для собак», а на другой — «15 кг». Обе надписи должны быть на одной коробке. Покупатель отметил в фильтрах «собака» и «вес от 10 кг». Имя и значение каждого условия должны совпасть в одном элементе массива. Это проверяет оператор $elemMatch (глава 2.6), а два условия объединяет $all.

В таблице — пять кормов каталога и проверка обоих условий.

z-02 корм для крупных породсобака15дада

В выводе два товара — те, у которых оба условия выполнены.

Если записать условие без $elemMatch, сервер проверяет имя и значение по разным элементам массива. Запрос ниже ищет переноски с нагрузкой от 30 кг. Вторая команда задаёт то же условие через $elemMatch и считает подходящие товары.

Первый запрос вернул переноску с нагрузкой 10 кг. Пара с именем «нагрузка» у неё есть, а число от 30 нашлось в других парах: длина 58, ширина 38, высота 36. С $elemMatch подходящих товаров 0. Оба запроса быстро работают на большом каталоге благодаря индексу из файла данных.

§4Один индекс на все характеристики

Предметный указатель в конце книги отсортирован по словам, а внутри слова — по страницам. Индекс { "attrs.k": 1, "attrs.v": 1 } отсортирован по имени характеристики, а внутри имени — по значению. Поле attrs — массив, поэтому индекс мультиключевой: в нём по записи на каждую пару каждого товара. На схеме — записи индекса с именем «вес».

Записи индекса с именем «вес»
attrs.kattrs.vТоварv ≥ 10
вес1z-04
вес1z-11
вес2z-01
вес12z-03читается

Записи идут по порядку значений. Сервер находит первую запись «вес, 10 и больше» и читает подряд до конца имени «вес».

Метод explain (глава 3.3) показывает стадию, с которой сервер начал чтение.

IXSCAN — чтение по индексу. Тот же индекс работает для «объёма», «мощности» и для характеристики, которой в каталоге ещё нет. Когда магазин заведёт аквариумы с характеристикой «литраж», индекс менять не придётся. Индекс ускоряет поиск. Покупателю нужен ещё список доступных фильтров.

§5Панель фильтров

Панель фильтров перечисляет категории и значения характеристик среди товаров, которые подходят под выбранные условия. Её строит стадия $facet (глава 4.8): две ветки конвейера обрабатывают одни и те же документы.

Сколько документов проходит через стадии
zoo_catalog · 12→$match вид кошка · 5→$facet
ветка categories→$group · 3 категории
ветка attributes→$unwind · 20 пар→без «вида» · 13→$group · 11 характеристик

Числа посчитаны по пяти товарам для кошек. У двух лекарств по две пары «вид», поэтому пар «вид» семь, и после их удаления остаётся 13 пар из 20.

  • Ветка categories считает товары по категориям. При равном числе порядок задаёт второй ключ сортировки.
  • Ветка attributes разворачивает пары стадией $unwind, убирает уже выбранный «вид» и собирает значения каждой характеристики в множество $addToSet. Выражение $sortArray упорядочивает значения.

В строке «нагрузка» два значения — 8 и 10 кг, по одному у каждой переноски. В строке «рецептурный» оба варианта, по одному лекарству. Панель не описана заранее ни для одной категории. Она собирается из характеристик найденных товаров. Новая категория получает фильтры в день, когда в каталог внесли первый товар. Похожая задача есть у анкет: вопросы в них тоже меняются.

§6Анкеты, у которых меняются вопросы

Бланки в поликлинике печатают новым тиражом, а заполненные старые бланки хранятся в карточках. Перед стерилизацией владелец заполняет анкету на сайте клиники. Анкету меняли. В версии 4 для кроликов добавили вес: дозу наркоза считают по весу. Вопрос о хронических болезнях перенесли в разговор с врачом. Старые анкеты остались в базе: по ним видно, на каких сведениях основывалось решение.

Вопросы двух версий анкеты на стерилизацию

age_monthsестьесть

Версия 3 — анкеты кошки и собаки, версия 4 — анкета кролика из вывода запроса.

Каждая анкета хранит номер версии формы version и ответы во вложенном документе answers. Такая раскладка называется шаблоном версионирования схемы. Документы старой и новой формы лежат в одной коллекции. По номеру версии программа выбирает, какие поля читать. Старые анкеты не переписываются: менять ответы задним числом нельзя. Поиск по вопросу, которого нет в части анкет, работает по своему правилу.

§7Поиск по вопросу, которого нет в части анкет

Перед наркозом собак и кошек не кормят: если животное ело утром, операцию переносят на более позднее время. Анестезиологу нужны анкеты с ответом «утром».

Ответ о последнем кормлении в четырёх анкетах
АнкетаФормаanswers.ate_lastПодходит
f-01 кошкастерилизация, v3вечером накануненет
f-02 собакастерилизация, v3утромда
f-03 собакавакцинация, v1поля нетнет
f-04 кроликстерилизация, v4сено без перерыванет

Анкета без поля не попадает в выборку: условие на отсутствующее поле ложно.

Подходит одна анкета — собака из f-02. Кролик ответил «сено без перерыва». Кроликов перед наркозом голодными не держат, и для них этот ответ верный. Запрос находит только точно совпадающие строки. Поэтому в формах с выбором ответа значения задают списком вариантов. Свободный текст запрос с таким условием пропустит.

Каталог и анкеты — две задачи одного типа: набор полей заранее не известен. Тот же тип данных встречается в других отраслях.

§10Проверьте себя

Почему каталог с отдельным полем на каждую характеристику плохо работает при тысячах категорий?

Для быстрого поиска по полю нужен индекс, а индексов на коллекцию не больше 64. В шаблоне атрибутов один индекс { "attrs.k": 1, "attrs.v": 1 } служит всем характеристикам.

Почему запрос без $elemMatch нашёл переноску с нагрузкой 10 кг?

Он проверял имя и значение по разным парам. Пара «нагрузка» у переноски есть, а число от 30 нашлось в парах длины, ширины и высоты.

Чем шаблон атрибутов отличается от EAV в реляционной таблице?

Пары лежат внутри документа товара, и товар читается целиком. Значения хранят свой тип: число остаётся числом и сравнивается как число.

Что даёт поле version в анкете?

По нему программа выбирает, какие поля читать в анкете. Документы разных версий лежат в одной коллекции и не переписываются.

Характеристикаattrs: [ { k: "вес", v: 15, u: "кг" } ]

Анкета{ form, version, answers: { … } }

Итог главы

Когда набор характеристик заранее не известен, их хранят массивом пар {k, v, u}. Один составной индекс по имени и значению ускоряет поиск по любой характеристике. Условие на пару записывают через $elemMatch, иначе имя и значение проверяются в разных парах. Панель фильтров строит стадия $facet из характеристик найденных товаров.

Анкеты с меняющимися вопросами хранят номер версии формы и ответы во вложенном документе. Старые анкеты не переписываются. Запрос по вопросу, которого нет в части анкет, эти анкеты не находит.
