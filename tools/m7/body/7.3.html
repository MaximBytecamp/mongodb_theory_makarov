§1Каталог, где у каждого товара свои характеристики

При клинике работает зоомагазин: корма, переноски, террариумы, лампы, лекарства, клетки. У корма важны вид животного, вес упаковки и возраст, у переноски — размеры и допустимая нагрузка, у лампы — мощность и доля ультрафиолета, у лекарства — нужен ли рецепт и как хранить. Покупатель выбирает товар через панель фильтров: отмечает «собака», «от 10 кг» и видит подходящие корма.

В большом интернет-магазине категорий тысячи, и у каждой свой список характеристик. Завести столбец под каждую нельзя: таблица станет широкой и почти пустой, а новая категория потребует перестройки. Отдельное поле в документе под каждую характеристику тоже создаёт трудность: искать по полю быстро можно только с индексом, а индексов на коллекцию — не больше 64.

В этой главе разобраны две задачи такого рода. Первая — каталог товаров: характеристики хранятся по шаблону атрибутов. Вторая — анкеты, у которых со временем меняются вопросы. Загрузите файл данных главы: он создаёт коллекции zoo_catalog (12 товаров) и zoo_forms (4 анкеты) и индекс по характеристикам.

§2Шаблон атрибутов

Общие для всех товаров поля — название, категория, цена — лежат на верхнем уровне документа. Характеристики собраны в массив attrs, где каждый элемент — пара «имя — значение»: k (key, имя), v (value, значение) и необязательная единица u. Так выглядят корм и террариум.

У двух товаров нет ни одной общей характеристики, кроме вида животного, а форма документов одинакова: массив пар. Значения сохраняют свой тип: вес 15 и объём 121 — числа, их можно сравнивать операторами $gte и $lt; вкус и материал — строки. В этом отличие от EAV в реляционной таблице, где все значения лежат в одном текстовом столбце.

Отдельные поля и массив пар

Слева каждой новой характеристике нужен свой индекс. Справа новая характеристика — новая пара в массиве, а индекс один на все.

§3Поиск по нескольким характеристикам

Покупатель отметил в фильтрах «собака» и «вес от 10 кг». Каждое условие относится к одной паре: имя и значение должны совпасть в одном и том же элементе массива. Для этого служит $elemMatch (глава 2.6), а два условия объединяет $all.

Подошли два корма: гипоаллергенный на 12 кг и для крупных пород на 15 кг. Корм для кошек на 2 кг отсечён обоими условиями, зерновая смесь на 1 кг — обоими. Без $elemMatch запрос { "attrs.k": "вес", "attrs.v": { $gte: 10 } } проверял бы имя и значение независимо: подошёл бы товар, у которого есть пара «вес» с малым значением и любая другая пара с числом от 10, например длина 58 см.

§4Один индекс на все характеристики

Файл данных создал составной индекс { "attrs.k": 1, "attrs.v": 1 }. Поле attrs — массив, поэтому индекс мультиключевой: в нём по записи на каждую пару каждого товара. Запрос с $elemMatch по имени и значению находит пары в индексе, не просматривая коллекцию. Метод explain (глава 3.3) показывает стадию, с которой сервер начал чтение.

IXSCAN — чтение по индексу. Индекс работает для любой характеристики: «вес», «объём», «мощность», и для характеристики, которой ещё нет в каталоге. Когда магазин добавит категорию аквариумов с характеристикой «литраж», индекс менять не придётся.

§5Панель фильтров

Панель фильтров строится по товарам, которые подходят под уже выбранные условия: какие категории есть и какие значения у каждой характеристики. Стадия $facet (глава 4.8) строит обе части панели за один запрос.

Для кошек нашлись пять товаров в трёх категориях. Ветка categories считает товары по категориям; при равном числе порядок задаёт второй ключ сортировки. Ветка attributes разворачивает пары стадией $unwind, убирает уже выбранный «вид» и собирает значения каждой характеристики в множество $addToSet, упорядоченное выражением $sortArray. В строке «нагрузка» два значения — 8 и 10 кг, у двух переносок; в строке «рецептурный» — оба варианта, по одному лекарству.

Панель не описана заранее ни для одной категории: она строится из характеристик тех товаров, которые есть в выборке. Для бизнеса это значит, что новая категория получает фильтры в день, когда в каталог внесли первый товар.

§6Анкеты, у которых меняются вопросы

Перед стерилизацией владелец заполняет анкету на сайте клиники. Анкету меняли: в версии 4 для кроликов добавили вес, потому что дозу наркоза считают по весу, а вопрос о хронических болезнях перенесли в разговор с врачом. Старые анкеты при этом остаются в базе — по ним видно, на каких сведениях основывалось решение.

Каждая анкета хранит номер версии формы version и ответы во вложенном документе answers. В версии 3 есть chronic, в версии 4 — weight_kg. Такой способ называют шаблоном версионирования схемы: документы старой и новой формы живут в одной коллекции, а программа по номеру версии понимает, какие поля ожидать. Старые анкеты не переписываются: изменить ответ задним числом нельзя, а пересчитывать тысячи документов ради нового вопроса не нужно.

§7Поиск по вопросу, которого нет в части анкет

Анестезиологу нужны животные, которые ели утром в день операции: наркоз им дают позже. Вопрос о последнем кормлении есть во всех версиях, а вот отвечают на него по-разному.

Подходит одна анкета — собака из f-02. Анкета перед вакцинацией f-03 этого вопроса не содержит и в выборку не попадает: условие на отсутствующее поле ложно. Кролик ответил «сено без перерыва» — кроликов перед наркозом не держат голодными, и для них этот ответ правильный. Запрос учитывает такие ответы, только если их перечислить, поэтому в формах с выбором ответа значения задают списком, а не свободным текстом.

§10Проверьте себя

Почему каталог с отдельным полем на каждую характеристику плохо работает при тысячах категорий?

Для быстрого поиска по полю нужен индекс, а индексов на коллекцию не больше 64. При шаблоне атрибутов один индекс { "attrs.k": 1, "attrs.v": 1 } покрывает все характеристики.

Зачем в запросе по характеристикам $elemMatch?

Он требует, чтобы имя и значение совпали в одном элементе массива. Без него условия проверяются по разным парам.

Чем шаблон атрибутов отличается от EAV в реляционной таблице?

Пары лежат внутри документа товара, и товар читается целиком. Значения хранят свой тип: число остаётся числом и сравнивается как число.

Что делает поле version в анкете?

Говорит программе, по какой форме заполнена анкета и какие поля в ней ожидать. Документы разных версий лежат в одной коллекции и не переписываются.

Итог главы

Когда набор характеристик заранее не известен, они хранятся массивом пар {k, v, u}. Один составной индекс по имени и значению ускоряет поиск по любой характеристике, условие на пару записывается через $elemMatch, а панель фильтров строится стадией $facet из характеристик найденных товаров.

Анкеты, у которых меняются вопросы, хранят номер версии формы и ответы во вложенном документе. Документы старых версий не переписываются, а запрос по вопросу, которого нет в части анкет, эти анкеты не находит.
